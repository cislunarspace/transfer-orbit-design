# 架构设计讨论记录

> 本文记录 transfer-orbit-design 从"独立工具集"转型为"e2m2e GUI 前端"的设计讨论过程。最终架构见 `architecture.md`，逐项决策见 `adr/`。

## 讨论日期

2026-08-04

## 问题

transfer-orbit-design 的现状不符合设计职能——它应该是 e2m2e 的 GUI，供用户方便地调用程序进行可视化。

## 现状分析

### 当前 tod 实际在做什么

tod 是 e2m2e 的"脚本编排层 + GUI"：40+ 个 Python 脚本，每个内部 `import e2m2e` 调用算法。GUI 通过 QProcess 子进程运行这些脚本。e2m2e 兼容层维持旧 import 路径。

### e2m2e 现状

- 五层架构（data/algorithm/api/tools/crates），v5.4.0
- Facade API 已实现 4/12 个方法：design_orbit, control_orbit, orbit_family_generation, orbit_stability
- CLI 是空壳
- 算法层 Python API 完整可用

### 核心痛点

1. 无内嵌可视化（弹窗 matplotlib）
2. 文件树不自动刷新
3. 管线无自动串联
4. 无结果缓存
5. 硬编码路径
6. SPICE 内核路径不在设置中

## 九轮追问与决策

### Q1: 执行后端策略
**选项**：A. Facade 直调 / B. e2m2e CLI / C. 混合 / D. 保持现状
**决策**：C（混合策略）— 已实现 Facade 的用直调，未实现的暂用旧脚本兜底
**最终演进**：用户选择只暴露已实现的 Facade 方法，其余灰掉 → 实质上变为纯 Facade 直调（ADR 0006）

### Q2: 数据管理架构
**选项**：A. 项目模型 / B. 统一数据注册
**决策**：引入 Project + Artifact 模型，output/ 作为持久化源（ADR 0008）

### Q3: 管线串联策略
**选项**：A. 显式管线 / B. 一键工作流
**决策**：A（显式管线）— Project 内自动注册，下一步的输入从 Artifact 列表选择

### Q4: 侧边栏组织方式
**选项**：A. 项目主导 / B. 工具主导 / C. 双面板折叠
**决策**：A（项目主导）— 用户视角是"我有什么数据"，不是"我能跑什么工具"

### Q5: Artifact 生命周期
**选项**：A. 自动持久化 / B. 手动保存 + 自动发现
**决策**：B — 复用 output/ 作为事实来源，GUI 启动时扫描重建（ADR 0008）

### Q6: 过渡策略
**选项**：A. 大爆炸替换 / B. 并行双模式 / C. 原地重构
**决策**：A（大爆炸替换）— 旧 GUI 架构与新架构不兼容（ADR 0007），核心代码迁入 `src/` 布局

### Q7: 大爆炸范围
**选项**：A. 全部灰掉 / B. 混合执行 / C. 算法层直调
**决策**：A — 只暴露 4 个已实现 Facade 方法，干净不带包袱（ADR 0006）

### Q8: 参数面板生成方式
**选项**：A. Pydantic 自动生成 / B. 手写 / C. 混合
**决策**：A（自动生成）— 零维护同步（ADR 0009）

### Q9: 可视化交互深度
**选项**：A. 最小可用 / B. 标准可用 / C. 完整体验
**决策**：B（标准可用）— 多轨道叠加 + 地月标注 + 2D 投影（ADR 0010）
